## 🏆 प्रमुख फ़ीचर - सॉवरेन व्हाइट-लेबल आर्किटेक्चर {#🏆-flagship-sovereign-white-label-architecture}

> **OwnPay पहला सेल्फ़-होस्टेड भुगतान प्लेटफ़ॉर्म है जो एक ही इंस्टॉलेशन पर पूरा व्हाइट-लेबल, मल्टी-ब्रांड, कस्टम-डोमेन चेकआउट आर्किटेक्चर लागू करता है।**
>
> कोई अन्य सेल्फ़-होस्टेड भुगतान गेटवे ऐसा नहीं करता।

इसका ठीक-ठीक मतलब यह है:

- **एक सर्वर, एक इंस्टॉलेशन** - जिसका मालिक एक सुपर-एडमिन है।
- **कई ब्रांड** - असीमित स्टोर (ब्रांड) बनाएँ। हर एक पूरी तरह से अलग इकाई है जिसका अपना कस्टम डोमेन, लोगो, नाम, रंग योजना, गेटवे, ग्राहक, लेजर और स्टाफ़ होता है।
- **हर ब्रांड के लिए कस्टम डोमेन** - `pay.yourbrand.com` को किसी ब्रांड से मैप करें। OwnPay DNS TXT रिकॉर्ड (`_ownpay-verification.{domain}`) के ज़रिए स्वामित्व सत्यापित करता है और A-record जाँच के ज़रिए रूटिंग की पुष्टि करता है, फिर डोमेन को सक्रिय करता है।
- **अदृश्य इंफ्रास्ट्रक्चर** - जब कोई ग्राहक चेकआउट पर पहुँचता है, तो वह `pay.yourbrand.com` पर आता है। उसे ब्रांड का लोगो, नाम और रंग दिखते हैं। OwnPay का कोई उल्लेख नहीं, कोई साझा डोमेन नहीं, कोई "powered by" संकेत नहीं, जब तक कि ब्रांड स्पष्ट रूप से उसे न जोड़े।
- **एडमिन पैनल निजी रहता है** - एडमिन डैशबोर्ड केवल मास्टर इंस्टॉलेशन डोमेन पर ही सुलभ है। कस्टम ब्रांड डोमेन सभी `/admin/*` पाथ के लिए 404 लौटाते हैं।
- **पूरा डेटा अलगाव** - हर ग्राहक रिकॉर्ड, ट्रांज़ैक्शन, लेजर प्रविष्टि, गेटवे क्रेडेंशियल और वेबहुक सीक्रेट डेटाबेस में `merchant_id` के ज़रिए हर ब्रांड तक सीमित है। ब्रांडों के बीच शून्य डेटा रिसाव।
- **ब्रांड-अवेयर URL** - सभी चेकआउट URL, गेटवे कॉलबैक URL और वेबहुक एंडपॉइंट `DomainUrlService` के ज़रिए ब्रांड के कस्टम डोमेन का उपयोग करके अपने-आप बनाए जाते हैं। इंस्टॉलेशन डोमेन कभी भी ग्राहक को दिखने वाले फ़्लो में लीक नहीं होता।

**परिणाम:** एक सर्वर। कई ब्रांड। हर ब्रांड एक पूर्ण, स्वतंत्र, पूरी तरह कस्टम-ब्रांडेड भुगतान गेटवे है - एक-दूसरे के लिए अदृश्य और OwnPay के लिए भी अदृश्य।

| ब्रांड निष्क्रियकरण | बिना डेटा खोए किसी ब्रांड को निलंबित करें |

## 2. कस्टम डोमेन और व्हाइट-लेबल पाइपलाइन {#2-custom-domain-&-white-label-pipeline}

| फ़ीचर | विवरण |
|:---|:---|
| कस्टम डोमेन मैपिंग | `op_domains` में किसी भी डोमेन को किसी ब्रांड के लिए रजिस्टर करें |
| DNS TXT सत्यापन | `_ownpay-verification.{domain}` TXT रिकॉर्ड डोमेन स्वामित्व साबित करता है |
| A-record जाँच | सक्रियकरण से पहले पुष्टि करता है कि डोमेन OwnPay सर्वर पर रूट होता है |
| स्वचालित DNS पुनः-जाँच | `DnsVerificationJob` cron लंबित/टूटे डोमेन को एक शेड्यूल पर फिर से जाँचता है |
| डोमेन मिडलवेयर | हर अनुरोध `HTTP_HOST` को सक्रिय डोमेन से मिलाता है और ब्रांड संदर्भ इंजेक्ट करता है |
| एडमिन पाथ ब्लॉकिंग | सभी कस्टम ब्रांड डोमेन पर `/admin/*` पाथ 404 लौटाते हैं |
| ब्रांड URL बिल्डर | `DomainUrlService` ब्रांड के डोमेन का उपयोग करके सभी चेकआउट, कॉलबैक और रीडायरेक्ट URL बनाता है |
| डोमेन कैश | इन-मेमोरी कैश एक अनुरोध चक्र के भीतर बार-बार DB लुकअप से बचाता है |

## 5. भुगतान प्रोसेसिंग {#5-payment-processing}

| फ़ीचर | विवरण |
|:---|:---|
| पेमेंट इंटेंट | यूनिक टोकन, राशि, मुद्रा, समाप्ति और मेटाडेटा के साथ परमाणु भुगतान अनुरोध |
| इंटेंट जीवनचक्र | `pending → processing → completed / failed / cancelled / expired` |
| टोकन-आधारित चेकआउट | चेकआउट URL में केवल एक सुरक्षित टोकन होता है; राशि और गेटवे विवरण कभी URL में उजागर नहीं होते |
| इंटेंट समाप्ति | cron पुराने इंटेंट को अपने-आप expired चिह्नित करता है और हुक चलाता है |
| मल्टी-करेंसी चेकआउट | ग्राहक किसी भी सक्षम मुद्रा में भुगतान कर सकता है |
| स्वचालित मुद्रा रूपांतरण | यदि कोई गेटवे केवल विशिष्ट मुद्राओं का समर्थन करता है, तो इंटेंट राशि अपने-आप परिवर्तित हो जाती है |
| रूपांतरण ऑडिट ट्रेल | मूल राशि, परिवर्तित राशि और विनिमय दर ट्रांज़ैक्शन रिकॉर्ड पर लॉग होते हैं |
| स्टेटस पोलिंग | रियल-टाइम स्टेटस अपडेट के लिए `GET /checkout/{token}/status` AJAX एंडपॉइंट |
| मैनुअल सत्यापन | SMS या ऑफ़लाइन गेटवे ट्रांज़ैक्शन एडमिन द्वारा मैन्युअल रूप से सत्यापित |

| ऑडिट ट्रेल | हर रिफ़ंड के लिए कारण, कर्ता और टाइमस्टैम्प संग्रहीत |
| लेजर पोस्टिंग | रिफ़ंड डबल-एंट्री लेजर में संतुलित डेबिट/क्रेडिट के रूप में अपने-आप पोस्ट होता है |

## 19. SMS-आधारित भुगतान सत्यापन {#19-sms-based-payment-verification}

| Regex टेस्टर | वास्तविक भुगतान प्रोसेस किए बिना किसी नमूना SMS बॉडी पर regex पैटर्न का परीक्षण करें |

## 22. शेड्यूल्ड जॉब (Cron) {#22-scheduled-jobs-cron}

| जॉब | उद्देश्य |
|:---|:---|
| `WebhookRetryJob` | विफल आउटबाउंड वेबहुक डिलीवरी को एक्सपोनेंशियल बैकऑफ़ के साथ फिर से भेजें |
| `QueueWorkerJob` | बैकग्राउंड जॉब क्यू प्रोसेस करें (ईमेल, एक्सपोर्ट, बल्क ऑपरेशन) |
| `BalanceVerificationJob` | लेजर बैलेंस की गेटवे द्वारा रिपोर्ट किए गए बैलेंस से क्रॉस-जाँच करें |
| `CurrencyUpdateJob` | लाइव विनिमय दरें प्राप्त और अपडेट करें |
| `SmsVerificationJob` | मैनुअल गेटवे के लिए लंबित SMS सत्यापन प्रोसेस करें |
| `RefundReconciliationJob` | गेटवे API से रिफ़ंड स्थिति सिंक करें |
| `DnsVerificationJob` | लंबित कस्टम डोमेन के DNS रिकॉर्ड फिर से जाँचें |
| `UpdateCheckJob` | नई OwnPay रिलीज़ के लिए पोल करें |
| `SystemUpdateJob` | कॉन्फ़िगर होने पर अपडेट अपने-आप लागू करें |

`GET /cron/{secret}` द्वारा ट्रिगर होता है। अलग-अलग जॉब को एडमिन सेटिंग्स पैनल से मैन्युअल रूप से भी चलाया जा सकता है।

| अंग्रेज़ी फ़ॉलबैक | अनुपलब्ध कुंजियाँ `config/languages/en.json` पर फ़ॉलबैक करती हैं |

## 25. सुरक्षा {#25-security}

| फ़ीचर | विवरण |
|:---|:---|
| AES-256-GCM एन्क्रिप्शन | ग्राहक PII और गेटवे क्रेडेंशियल रेस्ट पर एन्क्रिप्ट |
| Argon2id पासवर्ड | स्टाफ़ और एडमिन पासवर्ड Argon2id से हैश किए जाते हैं |
| bcrypt फ़ॉलबैक | अपग्रेड संगतता के लिए लीगेसी bcrypt समर्थन |
| CSRF सुरक्षा | प्रति-सेशन CSRF टोकन; सभी POST/PUT/DELETE के लिए मान्य टोकन आवश्यक |
| Content Security Policy | प्रति-अनुरोध nonce; सख्त नीति अनधिकृत इनलाइन स्क्रिप्ट को ब्लॉक करती है |
| HSTS | HTTP Strict Transport Security हेडर लागू |
| X-Frame-Options | `DENY` - क्लिकजैकिंग रोकता है |
| X-Content-Type-Options | `nosniff` - MIME स्निफ़िंग रोकता है |
| Referrer-Policy | रेफ़रर जानकारी के रिसाव को सीमित करता है |
| SSRF सुरक्षा | `UrlValidator` वेबहुक URL को रिज़ॉल्व करके सत्यापित सार्वजनिक IP पर पिन करता है; रीडायरेक्ट-फ़ॉलोइंग ब्लॉक |
| रेट लिमिटिंग | प्रति-रूट, प्रति-IP स्लाइडिंग विंडो; `Retry-After` हेडर के साथ 429 |
| लॉगिन थ्रॉटलिंग | लॉगिन, पासवर्ड रीसेट और OTP एंडपॉइंट के लिए सख्त बकेट |
| हैश-आधारित PII खोज | ईमेल/फ़ोन हैश के रूप में संग्रहीत; लुकअप के लिए कभी डिक्रिप्शन की ज़रूरत नहीं |
| लॉग सैनिटाइज़ेशन | `LogSanitizer` सभी लॉग आउटपुट से पासवर्ड, टोकन और कार्ड डेटा हटाता है |
| SQL इंजेक्शन रोकथाम | हर जगह पैरामीटर बाइंडिंग के साथ prepared statements |
| XSS रोकथाम | Twig autoescaping हमेशा चालू; `|raw` केवल विश्वसनीय सामग्री पर |

## 26. सेल्फ़-अपडेट इंजन {#26-self-update-engine}

| फ़ीचर | विवरण |
|:---|:---|
| वर्ज़न ट्रैकिंग | कॉन्फ़िग में मौजूदा वर्ज़न; `op_update_history` सभी लागू अपडेट लॉग करता है |
| अपडेट मैनिफ़ेस्ट | उपलब्ध रिलीज़ मेटाडेटा के लिए अपडेट सर्वर को पोल करता है |
| अपडेट-पूर्व बैकअप | कोई भी अपडेट लागू करने से पहले स्वचालित डेटाबेस + फ़ाइल बैकअप |
| SHA-256 + RSA सत्यापन | एक्सट्रैक्शन से पहले डाउनलोड को checksum और RSA सिग्नेचर द्वारा सत्यापित किया जाता है |
| Zip-slip सुरक्षा | एक्सट्रैक्शन रिलीज़ आर्काइव में पाथ ट्रैवर्सल हमलों को ब्लॉक करता है |
| स्कीमा माइग्रेशन | रिलीज़ में DB बदलाव अपने-आप लागू होते हैं |
| रोलबैक | सत्यापन विफल होने पर बैकअप से पुनर्स्थापित करता है |
| मेंटेनेंस मोड | अपडेट के दौरान सिस्टम मेंटेनेंस में जाता है; सफलता पर अपने-आप बाहर निकलता है |
| मैनुअल + ऑटो मोड | एडमिन मैन्युअल रूप से ट्रिगर करता है या cron के ज़रिए ऑटो-अपडेट चालू करता है |
